# 01 技术选型分析

> 本文档对"土豆聊天(T Potato Messenger)"即时通讯系统的候选技术栈进行对比分析,并给出最终选型结论。
> 选型原则:**现代化、契合 IM 实时场景、团队上手成本低、生态成熟、可部署到 SECoder(K8s)**。

## 1. 总体架构约束(来自需求文档)

需求文档已经规定了若干架构约束,选型必须在此框架内进行:

- **前后端分离**,通过 API 契约通信(本仓库通过 `docs/02-API约定.md` 约定);
- **Nginx 作为反向代理入口**,前端静态资源 + API/WS 转发;
- 后端划分为四个逻辑模块:**用户账户、好友关系、会话管理、消息系统**;
- 数据库使用 **MySQL**;
- 实时性:**WebSocket 长连接推送 + REST 拉取兜底**(消息链 / cursor 一致性校验);
- 部署平台:**SECoder(Kubernetes)**,需容器化与 CI/CD。

## 2. 前端框架对比

| 维度 | Vue 3 ✅ | React 18 | Svelte 5 | SolidJS |
|---|---|---|---|---|
| 学习曲线 | 平缓,模板语法直观 | 中等,JSX + hooks 心智负担 | 平缓 | 陡峭 |
| 响应式模型 | 基于代理(Proxy),细粒度自动追踪 | 手动 `useState`/`memo` | 编译期响应式,极致细粒度 | 编译期细粒度 |
| TypeScript 支持 | 一流(Vue 3 用 TS 重写) | 一流 | 良好 | 良好 |
| 中文生态/文档 | **极佳**(Vue 作者及社区中文资源丰富) | 好(翻译文档) | 一般 | 一般 |
| 组件库(中文向) | Naive UI / Element Plus / Ant Design Vue 三足鼎立 | Ant Design 等 | 组件库少 | 组件库少 |
| 课程一致性 | 课程示例与讲义均以 Vue 演示 | — | — | — |

**结论:Vue 3。** IM 界面以"列表渲染 + 高频局部更新(新消息气泡、未读角标)"为主,Vue 的自动细粒度响应式天然契合;中文资料和组件库生态最全;与课程讲义一致,便于答辩。

## 3. 前端组件库对比

| 维度 | Naive UI ✅ | Element Plus | Ant Design Vue |
|---|---|---|---|
| TypeScript | **原生 TS 编写,类型一等公民** | 后补类型 | 后补类型 |
| 包体积 | **全量 tree-shaking,无需引入样式文件** | 较大,需引入样式 | 较大 |
| 主题定制 | **JS 对象主题,暗色模式开箱即用** | CSS 变量,较死板 | ConfigProvider,较重 |
| 组件覆盖 | 90+ 组件,表单/弹窗/通知/头像齐全 | 最全,企业组件多 | 全 |
| 社区规模 | 中等 | 最大 | 大 |

**结论:Naive UI。** 聊天界面的核心部分(消息气泡、会话列表、时间轴)必须自定义实现,组件库只承担表单、弹窗、下拉、通知、输入框等通用部分——这正是 Naive UI 的舒适区。其原生 TS、按需加载与 JS 主题定制(方便实现深色模式)与本项目 Vue 3 + TS 技术栈高度契合;其社区规模小于 Element Plus 的劣势,在自定义 UI 占比高的 IM 场景下并不构成问题。

## 4. 后端框架对比

| 维度 | FastAPI ✅ | NestJS | Express | Go (Gin) | Spring Boot |
|---|---|---|---|---|---|
| WebSocket 支持 | **原生一等支持** | 原生网关 | socket.io | gorilla/websocket | STOMP/原生 |
| API 契约即代码 | **Pydantic 模型即契约,自动生成 OpenAPI 文档** | 装饰器 + DTO | 需手写 Swagger | swaggo 注释 | springdoc |
| 开发效率 | 高 | 中(样板多) | 高但缺规范 | 中 | 低(样板多) |
| 类型安全 | Pydantic 运行时校验 + mypy | TS 编译期 | TS 可选 | 编译期强类型 | 强类型 |
| 异步/并发 | **asyncio,长连接友好** | Node 事件循环 | 事件循环 | goroutine | 虚拟线程较新 |
| 课程一致性 | 讲义明确赞赏 Pydantic 定义 API | 课程示例用 Express | 课程示例 | — | — |
| 部署镜像体积 | 中(~200MB) | 小 | 小 | **极小** | 大 |

**结论:FastAPI。** 课程讲义明确推荐"通过类型系统(Pydantic)加上注释定义 API,让代码本身成为 Source of Truth",FastAPI 是这一理念的最佳实践:Pydantic 模型自动生成 `/docs` OpenAPI 文档,前后端可据此对齐契约;原生 async WebSocket 端点契合"长连接推送 + REST 兜底"的消息架构;开发效率高,适合一学期的课程节奏。Go 在性能上有优势,但对课程项目而言开发速度与可维护性优先。

## 5. 数据库与 ORM

| 维度 | MySQL 8 ✅ | PostgreSQL | SQLite(dev) |
|---|---|---|---|
| 需求文档 | **明确指定** | 未指定 | 不适合生产 |
| 事务/索引 | 完备 | 更强(部分场景) | 单机 |
| 运维熟悉度 | 课程环境广泛使用 | 较高 | — |

**结论:生产使用 MySQL 8(遵循需求文档);ORM 使用 SQLAlchemy 2.0(async 支持成熟)。** 本地开发默认使用 SQLite 零配置启动,通过环境变量 `DATABASE_URL` 一键切换到 MySQL,`docker-compose` 与 SECoder 环境均指向 MySQL。

## 6. 实时通道:WebSocket vs SSE vs 轮询

| 方案 | 延迟 | 服务端推送 | 双向 | 结论 |
|---|---|---|---|---|
| 短轮询 | 差(秒级) | ✗ | ✗ | 仅作为 Level 1 教学演示,不采用 |
| 长轮询/SSE | 中 | ✓ | ✗(SSE) | 无法承载客户端 ACK/心跳上行 |
| **WebSocket ✅** | **优(<200ms 达标)** | ✓ | ✓ | **需求文档明确要求,最终方案** |

采用需求文档的**推拉结合**模型:在线用户走 WebSocket 推送,推送失败或断线时通过 REST `GET /api/v1/sync` 按 cursor 拉取兜底;推送包携带 `prev_cursor`,客户端校验连续性,发现缺口立即补拉。

## 7. 鉴权方案:JWT vs Session

- 课程讲义列出 Cookie+Session 与 Token(JWT)两种主流方案;
- 本项目为**前后端分离 + WebSocket 双通道**,WebSocket 握手阶段无法方便地携带 Cookie 跨域凭证(需 `withCredentials` 配合),而 URL query token 简单直接;
- 后端需要无状态部署(SECoder 多副本),Session 需要额外共享存储(Redis)。

**结论:JWT(Access Token,短有效期)。** 密码使用 bcrypt 加盐哈希存储,敏感操作(改密码)要求旧密码验证。Token 通过 `Authorization: Bearer` 头传递,WebSocket 通过 `?token=` 传递。

## 8. 最终选型一览

| 层 | 选型 |
|---|---|
| 前端框架 | Vue 3 + TypeScript + Vite |
| 状态管理 | Pinia |
| UI 组件库 | Naive UI |
| 后端框架 | FastAPI + Pydantic v2 |
| ORM / 迁移 | SQLAlchemy 2.0 |
| 数据库 | MySQL 8(生产)/ SQLite(本地默认) |
| 鉴权 | JWT + bcrypt 加盐哈希 |
| 实时通道 | WebSocket(推送)+ REST cursor 拉取(兜底) |
| 反向代理 | Nginx |
| 容器化 | Docker + docker-compose |
| 部署 | SECoder(Kubernetes)|
