## 模块：消息分发主干（会话链 + 用户链 + 推送/补拉）

> 这不是某一个需求点，而是 D 侧所有需求的共同底座。答辩时若被问「你们的消息为什么不会丢」，
> 就讲这一节。

### 需求点原文

需求文档把消息生命周期拆成四步：**消息发送 → 消息分发 → 消息送达 → 消息处理**；
并在系统基本要求里要求「具有可靠完整的消息送达机制」（数据完整性），附录要求长连接与三个时机的消息同步。

### 实现方式

采用**三链结构**，写入口只有一个：

```
① 会话链 message          一条消息只写一行（conversation_id, sender_id, body, reply_to, create_time）
        ↓ 写扩散
② 用户链 inbox_message    为每个成员各写一行，kind=message；这一行的自增主键 id 就是该用户的 seq
        ↓
③ 在线推送 / 离线补拉      在线：WebSocket 推 message.new；离线/断线/发现缺口：GET /sync 按 seq 增量拉
```

**为什么是「会话链 + 用户链」双写，而不是只存一份？**

- 只存会话链：拉历史必须按会话扫描，无法表达「每个用户自己的投递状态」。已读位置、未读数、
  离线补拉都以用户为维度，缺这一维就只能靠额外表或全量扫描去凑。
- 只存用户链：同一条消息在 N 个成员处重复 N 份，`msg_id` 与内容的唯一性无处约束。
- 因此：**内容与会话维度放会话链（唯一），投递与顺序放用户链（每用户一条）**。
  这也让已读位置天然可以表达为「我的用户链上读到第几号」，不需要另建已读表。

**为什么用 `prev_seq` 做连续性校验（而不是靠时间戳或消息 ID）？**

推送是异步的、可能丢失或乱序。客户端维护本地 cursor（上次处理到的 seq），每条推送都带上
`seq`（本条）与 `prev_seq`（本条之前那一条）。客户端只需比较 `prev_seq` 与本地 cursor：

- 相等 → 顺序连续，推进 cursor；
- 不相等 → 中间缺了东西，立即 `GET /sync?cursor=本地cursor` 补齐。

这个判断是 O(1) 的、不依赖时钟、也不需要服务端记录「谁收到了什么」。
**发送方与接收方的 prev_seq 可能不同**（同一条消息在不同用户链上的前后邻居不同），
所以推送必须按用户分别构造事件——这正是 `send_message` 返回值是 `{user_id: 事件}` 的原因。

**为什么命令消息（已读/撤回/删除）也占用 seq？**

如果命令消息不占用 seq，它在用户链上就没有位置，`/sync` 无法按 seq 增量地把「这条被撤回了」
「我读到第几条了」告诉离线端——离线期间发生的状态变化就丢了。让命令消息占用 seq 并随链下发，
离线端补拉一次即可复原全部状态，**不需要为每类状态各造一套同步机制**。

### 关键代码位置

| 位置 | 职责 |
|---|---|
| `backend/app/services/message_service.py` → `send_message()` | 写会话链 → 为每个成员写用户链 → 逐个构造带 `seq`/`prev_seq` 的推送事件；发送者自己的 `read_index` 顺带推进 |
| `backend/app/services/message_service.py` → `recall_message()` | 撤回：改写 `message.body` 为占位文本 + 向所有成员投递 `kind="recall"` 命令消息 |
| `backend/app/services/message_service.py` → `last_seq_of_user()` | 读某用户链尾；`prev_seq` 与已读上限校验都依赖它（**必须在插入新行之前调用**） |
| `backend/app/api/v1/sync.py` → `sync()` | 按 `id > cursor ORDER BY id LIMIT n` 增量拉取，`limit+1` 探测是否还有更多 |
| `backend/app/api/v1/messages.py` → `send_message()` / `conversation_history()` | 发送入口（含回复校验）；历史按会话链游标翻页 |
| `frontend/src/api/ws.ts` → `handleEvent()` | 客户端侧连续性校验：`prev_seq !== localSeq` 即调 `resync()` |

### 验证方式

- 用例：`backend/tests/test_message_flow.py`（发送/撤回/历史/未读）、`test_websocket.py`
  （推送送达、`prev_seq` 连续、发送方也收到推送、多端连接都收到、离线端改走 `/sync`）。
- 手工：两个浏览器各登录一个账号，A 发消息，B 秒收；断开 B 的网络再发，B 恢复后经 `/sync` 补齐。
- 数据层：`sqlite3 backend/potato.db "select id,user_id,kind,msg_id from inbox_message order by id"`，
  可直接看到「一条消息在用户链上有 N 行、seq 各不相同」。

### 答辩追问准备

| 可能的追问 | 回答要点 |
|---|---|
| 群成员很多时写扩散会不会成为瓶颈？ | 会，写入量随成员数线性增长。当前是课程项目的务实选择：它换来的是「每个用户的投递状态天然可查」，无需额外的扩散任务与状态表。优化方向是写扩散改为「读时合并 + 活跃成员推送」（见模块：实时性与可靠性） |
| 用户链会不会无限增长？ | 会。当前每个会话的每条消息在每个成员处永久保留一行（删除除外）。这是「离线补拉能回溯全部历史」的代价，需求明确要求新成员可看入群前历史，因此暂不做裁剪 |
| 会话链和用户链会不会不一致？ | 两者在同一事务内写入并一起 `commit`，不存在中间态对外可见的情况。`msg_id` 外键 + `ON DELETE CASCADE` 兜住孤儿行 |
| seq 是全局唯一还是每用户唯一？ | 每用户唯一。`inbox_message.id` 是全局自增，但语义上的 seq 只在「同一个 user_id 内」连续，跨用户不保证连续——所以推送里的 seq 只对收件人本人有意义 |

## 模块：已读与未读状态

> 对应需求文档第 3 页 通用·**未读计数**（4 分）。提交 `e82bf67`。

### 需求点原文

> 未读计数：显示每个会话的未读消息数，打开会话后清零。

### 问题（改之前是三处偏差叠加）

| 编号 | 偏差 | 后果 |
|---|---|---|
| 1 | `mark_read()` 无条件写入新值 | 请求乱序（旧请求后到）会把已读位置**写小**，未读数反弹 |
| 2 | 只校验了 `read_index ≥ 0`，没有上限 | 传 `read_index=999999999` 即可把未读**一次性清零**，且无法与「真的读完了」区分 |
| 3 | 前端 `chat.ts` 用 `latest.msg_id` 上报 | `msg_id` 是**全局消息 ID**，`read_index` 的契约含义是**我的用户链 seq**，两者不是一回事。表现为打开会话就报一个远超实际的值，未读被误清零 |

第 3 条最隐蔽：前端用 `.catch(() => undefined)` 把错误吞掉了，界面上看不出任何异常——
**未读数看起来「正常工作」（永远是 0）**。这也是为什么第 2 条的修复必须和第 3 条一起做：
一旦加上上限校验，前端原本的每一次上报都会被判越界拒绝（400），未读计数会从「悄悄算错」
变成「彻底不动」；两者分开交付，中间会留下一个更糟的坏状态。

### 实现方式

**后端：两条约束 + 一次链上留痕**

```python
# backend/app/services/message_service.py
def mark_read(db, member, read_index) -> ReadSyncEvent | None:
    upper = last_seq_of_user(db, member.member_user_id)
    if read_index > upper:
        raise bad_request("已读位置超过该用户收到的最新消息序号")   # ② 有上限：拒绝，不截断
    if read_index <= member.read_index:
        return None                                            # ① 单调：旧请求忽略，不写链不推送
    ...
    row = InboxMessage(kind="read", payload={"conversation_id": ..., "read_index": read_index})
    db.flush()                                                  # ③ 占用一个 seq，供多端/离线同步
    return ReadSyncEvent(seq=row.id, prev_seq=prev_seq, ...)
```

- **① 单调**：`read_index` 的语义是「我已读到我的用户链第几号」，它只能增长。旧值到达即视为
  迟到的重复请求，不改状态、不推送，接口仍返回成功（与最新状态一致，不制造假错误）。
  这也让「重复上报同一个值」不会往用户链里灌垃圾行。
- **② 有上限**：调用方（客户端）只可能读到确实投递给它的条目，因此超过用户链尾的值
  必然是伪造或客户端状态异常 —— **直接拒绝 `400/1001`，而不是截断**。截断等于照旧把未读
  清零，反而掩盖了客户端的 bug，与「把问题藏起来」没有区别。这与 `read_index < 0`
  原本就被 schema 拒绝的做法风格一致。
- **③ 链上留痕**：成功上报会向用户链写入一条 `kind="read"` 命令消息，占用一个 seq。
  于是「我在手机上读了」这件事能被推送给我的其他端（`read.sync`），也能被离线端通过
  `/sync` 补拉出来——**多端一致不需要为已读单独造一套同步机制**。

**未读数口径**：`seq > read_index` 且 `kind="message"` 且未被删除的条数（第三项见下一节）。

**前端：上报正确的值**

会话历史接口为每条消息返回它在**当前用户**用户链上的 `seq`（新增增量字段
`MessageOut.seq`），前端改为：

```ts
// frontend/src/stores/chat.ts
const readIndex = latest.seq          // 不是 latest.msg_id
if (readIndex === undefined) return
await api.markRead(conversationId, readIndex)
```

同时去掉了 `.catch(() => undefined)`：静默吞错正是第 3 条偏差长期没被发现的原因。

**`read.sync` 事件补齐 `seq`/`prev_seq`**：已读上报既然占用了一个 seq，客户端就必须对它做
与 `message.new` 相同的连续性校验，否则本地 cursor 会被 read 条目打断，之后每条推送都被
误判成「有缺口」而反复补拉。前端 `ws.ts` 的 `handleEvent` 因此对三类事件统一处理：

```ts
if (event.type === 'message.new' || event.type === 'message.recall' || event.type === 'read.sync') { ... }
```

| 位置 | 职责 |

### 答辩追问准备

| 可能的追问 | 回答要点 |
|---|---|
| 为什么越界要报错，而不是直接按最大值截断？ | `read_index` 的含义是「客户端实际读到过的位置」，越界说明客户端状态异常或伪造。截断会把未读清零、看起来「功能正常」，从而掩盖客户端 bug；拒绝能让问题立刻暴露。错误码 `1001` 与 schema 拒绝负数时保持一致 |
| 已读位置为什么要写入用户链（多一条记录）？ | 为了多端一致与离线同步。离线端无法收到 `read.sync` 推送，只能靠 `/sync` 增量恢复「我在别的端读到哪了」；命令消息占用 seq 后，这一状态就随链自然下发，不需要额外机制 |
| 未读数是实时算的还是缓存的？ | 实时算（`SELECT count(*)`，条件 `seq > read_index`）。当前数据量下开销可接受；若成为瓶颈，可在 `conversation_member` 上加冗余计数（见模块：实时性与可靠性） |
| 多个会话同时有未读，`read_index` 会不会串？ | 不会写错，但要注意语义：`read_index` 是**用户链上的全局位置**，不是「某会话的位置」。因此它天然 ≥ 某些会话里的消息 seq——这也是删除消息时需要回压 `read_index` 的原因（见下一节） |
| 为什么发送者自己的已读位置在发消息时就推进？ | 自己发的消息对自己显然已读。若不推进，发送者每发一条都会给自己增加一个未读 |

## 模块：历史记录 · 本地删除与多端一致

> 对应需求文档第 3 页 通用·**删除记录**（1 分），并同时支撑「数据完整性」。
> 提交 `dfb99c4`。

### 需求点原文

> 删除记录：用户可以删除自己会话中的聊天记录（删除仅对自己生效）。

### 问题（整条链路原本不可用）

| 编号 | 问题 | 后果 |
|---|---|---|
| 1 | 删除是在用户链上**物理删行**，而会话历史查的是 `message` 表 | 被删消息**从历史里复活**：刷新或重进会话又出现了 |
| 2 | `/sync` 同样查不到删除痕迹 | 其他设备永远不会知道这条被删了；若删的是「还没同步过去」的消息，反而会更混乱 |
| 3 | `message.delete` 事件从未推送，前端也没有 `deleteMessage` 门面 | **UI 根本没有删除入口**，功能实际不可用 |
| 4 | 未读数按用户链统计 | 删掉的消息已经被物理删行，未读数与历史看不到的消息出现口径矛盾 |

### 实现方式：把删除写成「投递墓碑」

删除时**不删行**，而是把用户链上那条记录**改写**成 `kind="delete"`，并写入
`payload={"msg_id": ..., "conversation_id": ...}`：

```
删除前： inbox_message(id=7, user_id=B, kind="message", msg_id=42, payload=NULL)
删除后： inbox_message(id=7, user_id=B, kind="delete",  msg_id=42, payload={"msg_id":42,"conversation_id":3})
         ↑ 同一个 id（seq 不变），只是换了类型与载荷
```

然后**会话历史、`/sync`、未读数三处共用同一个子查询**做过滤：

```python
# backend/app/services/message_service.py
def deleted_msg_ids(user_id: int):
    return select(InboxMessage.msg_id).where(
        InboxMessage.user_id == user_id, InboxMessage.kind == "delete", InboxMessage.msg_id.is_not(None))
```

- 历史：`WHERE message.msg_id NOT IN (deleted_msg_ids(me))` —— 已删的不出现；
- `/sync`：排除「已删除的投递行」，但**墓碑行本身照常下发**（`kind="delete"` + `payload`），
  客户端据此从本地列表移除；离线端下次补拉也能拿到，**不会再复活**；- 未读：`kind="message"` 且未被墓碑标记 —— 与历史口径一致，不再出现「看不到却还算未读」。

**为什么用墓碑而不用新增字段（如 `deleted` 布尔列）？**

`inbox_message.kind` 的枚举在 `docs/03` 里**本来就列了 `delete`**，语义位置是现成的。
更重要的是运维现实：生产库是挂在持久卷上的 SQLite（有真实数据），建表走
`Base.metadata.create_all`——**它只会建缺失的表，不会给已存在的表加列**。加字段意味着要写
迁移脚本并在有数据的库上执行，风险与工作量都远高于复用现有行。
墓碑方案把 DDL 与停机风险降到了零。

**为什么墓碑行沿用原来的 `id`（seq）？**

若换一个新 id，删除操作会消耗一个 seq 并把原来的 seq 空掉，客户端的 cursor 就会出现
「空洞」，连续性校验会误判为丢消息。沿用原 id 则链是连续的，删除只是「那一行的类型变了」。

**边界：我删除一条自己没有投递记录的消息**

群成员的投递行只在「成为成员之后」才产生。新成员去删除**入群前的历史消息**时，用户链上
根本没有对应行——此时补写一条墓碑行，保证历史与 `/sync` 口径一致。

> 这里踩到一个会 500 的坑：新建墓碑行时 `row.id` 在 `db.flush()` 之前是 `None`，
> 而随后的「已读位置回压」逻辑要拿它和 `read_index` 比较，直接抛 `TypeError`。
> 触发条件恰好就是上面这个边界。修法是先 `flush()` 取到 id，并加 `row.id is not None` 兜底，
> 同时补了 `test_delete_message_without_my_delivery_row` 用例。

**已读位置回压（一个必须处理的连带影响）**

`read_index` 是用户链上的位置。若删除的消息排在 `read_index` **之前**，保留原 `read_index`
的话，它会指向一个已变成墓碑的 seq；客户端随后基于「历史可见的最后一条 seq」上报已读时，
这个值会小于 `read_index`，被单调约束判成「回退」而**永久失效**。
因此删除时把 `read_index` 压到被删消息之前：

```python
if member is not None and row.id is not None and member.read_index > row.id:
    member.read_index = row.id
```

**取舍（答辩要能讲清）**：回压会让「被删消息与其后的消息」重新算作未读——用例里未读数
由 1 变成 2。这是刻意选的保守方向：**多算一条未读只是界面多一个红点，少算一条会让人漏看
消息**。若评委认为「删除不应影响未读数」，这条语义需要调整（改为不统计被回压区间，或让
客户端的上报带上「已读位置不回退」的标记）。

**前端**

- 新增 `deleteMessage` 门面与 chat store 的删除动作（先落服务端，再更新本地列表）；
- 消费 `message.delete` 事件：同一账号的其他设备同步移除；
- 登录补拉 `/sync` 时也应用 `kind="delete"` 标记 —— 否则刷新后已删消息会重现。

### 答辩追问准备

| 可能的追问 | 回答要点 |
|---|---|
| 删除是只对自己生效还是对所有人？ | 只对自己（`DELETE .../messages/{msg_id}` 仅改我自己用户链上的行）。对方的历史、未读、同步都不受影响——用例 `test_delete_message_is_local_only` 就是断言这一点 |
| 为什么不物理删除？ | 物理删行会导致「历史查 `message` 表、同步查 `inbox_message` 表」两条路径口径不一致，被删消息会复活；而且无法把删除这件事告诉离线端。墓碑让两条路径按同一规则过滤，并让删除本身成为可同步的事件 |
| 墓碑会不会越积越多？ | 会，但一条墓碑只占一行，且它替代了原本那一行（改写而非新增），用户链长度不变。清理策略可与「用户链裁剪」一并考虑 |
| 群主撤回消息和用户删除消息有什么区别？ | 撤回（`recall`）改的是**共享的** `message.body` 并向**所有成员**投递命令消息，所有人都看到「已撤回」；删除只改**我自己的**用户链，别人看不到任何变化 |
| 删除后未读数为什么可能变大？ | 见上文「已读位置回压」的取舍。这是为了保证已读上报不回退而付出的代价，方向选了「宁可多算」 |
| `/sync` 返回的 `kind="delete"` 条目客户端怎么用？ | 用 `payload.msg_id` 从本地消息列表移除；登录补拉时同样应用，避免刷新后重现 |

## 附：答辩现场可用的三个「改前 vs 改后」对比

答辩时最有说服力的不是讲代码，而是**演示一个真实缺陷被修掉**。以下三个都能用两个浏览器现场演：

| 演示 | 改前表现 | 改后表现 | 涉及需求点 |
|---|---|---|---|
| 打开会话看未读数 | 未读数永远是 0（前端上报了错误的 `msg_id`，且被静默吞错） | 收 3 条显示 3，打开后变 0 | 未读计数（4 分） |
| 删除一条消息后刷新 | 被删消息**复活** | 不再出现；其他设备/刷新后一致 | 删除记录（1 分） |
| 伪造已读位置 | `{"read_index": 999999999}` 直接清零未读 | 返回 `400/1001`，未读不受影响 | 未读计数（4 分） |

第三个演示尤其适合回答「你们怎么保证数据是可信的」：**服务端不信任客户端上报的位置，
因为它只可能读到确实投递给它的条目**。
